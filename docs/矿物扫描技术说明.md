# Minecraft 矿物扫描技术说明

本文说明本目录中的扫描器如何从 Minecraft Java 世界文件中找到矿物方块，并将坐标写入按距离排序的 Excel。说明以 Minecraft Java 1.21.x 的 Anvil 区块格式为主。

核心实现位于：

- `generic\scan_to_excel.py`：通用扫描入口，推荐使用。
- `actual-run\scan_diamonds.py`：本次钻石扫描使用的扫描器核心。
- `actual-run\export_nether_debris_excel.py`：将同一核心切换为下界远古残骸扫描。

## 一、扫描的输入是什么

Minecraft Java 世界不会把每个方块保存成一个独立文件，而是分层保存：

```text
世界目录
|-- region\r.<regionX>.<regionZ>.mca          主世界
|-- DIM-1\region\r.<regionX>.<regionZ>.mca    下界
`-- DIM1\region\r.<regionX>.<regionZ>.mca     末地
```

一个 region 文件包含最多 32×32 个区块，也就是最多 1024 个区块。文件开头有两个 4 KiB 的表：

1. 第一个表是 location table，记录每个区块在文件中的 sector 起始位置和 sector 数量。
2. 第二个表是时间戳表。

每个 sector 固定为 4096 字节。脚本只需要先读取第一个 4096 字节，就可以知道目标区块是否存在，以及它的 NBT 压缩数据位于文件的哪个 sector。

## 二、从区块坐标定位 region

脚本接收目标区块坐标范围，例如：

```text
min_chunk = -250
max_chunk = 249
```

每个区块坐标转换到 region 坐标和 region 内局部坐标：

```python
region_x, local_x = divmod(chunk_x, 32)
region_z, local_z = divmod(chunk_z, 32)
```

这里必须使用 Python 的 floor division 语义。负坐标不能简单使用向零截断，否则 `chunk=-1` 会被错误地放到 region 0；正确结果是：

```text
chunk -1 -> region -1, local 31
chunk  0 -> region  0, local  0
```

location table 中的条目索引为：

```python
entry = 4 * (local_x + local_z * 32)
```

三字节 sector offset 使用大端序读取：

```python
offset = (header[entry] << 16) | (header[entry + 1] << 8) | header[entry + 2]
```

offset 为 0 表示该区块没有保存数据。扫描器只扫描用户要求的 `min_chunk..max_chunk` 方形，不会把同一个 region 中不属于目标范围的区块算进去。

## 三、读取和解压区块 NBT

区块记录的格式是：

```text
4 字节：压缩 payload 长度
1 字节：压缩类型
剩余内容：压缩后的 NBT 数据
```

扫描器支持：

```text
压缩类型 1：gzip
压缩类型 2：zlib
压缩类型 3：未压缩
```

脚本使用 `nbtlib.File.parse(io.BytesIO(payload))` 解析 NBT。扫描是只读操作，不会把修改后的 NBT 写回 region 文件。

读取时必须保证服务端已经执行 `save-all flush` 并停止，或者至少不再写入目标 region 文件。正在写入时读取可能得到不完整的 length、sector 或压缩 payload。

## 四、进入 sections 和 block_states

一个区块由多个垂直 section 组成。每个 section 通常覆盖 16×16×16 个方块，并有一个 section 坐标 `Y`：

```text
section_world_y = section_Y * 16
```

区块 NBT 中的关键结构大致如下：

```text
root
`-- sections[]
    |-- Y
    `-- block_states
        |-- palette[]
        `-- data[]
```

`palette` 是本 section 中实际出现的方块状态列表。列表中的状态包含 `Name`，例如：

```text
minecraft:stone
minecraft:deepslate
minecraft:diamond_ore
minecraft:deepslate_diamond_ore
minecraft:ancient_debris
```

扫描器先遍历 palette，只记录目标 block ID 对应的 palette index。例如指定：

```text
--ore minecraft:diamond_ore=钻石
--ore minecraft:deepslate_diamond_ore=深板岩钻石
```

如果当前 section 的 palette 不包含目标 ID，直接跳过整个 section，不解码它的 4096 个方块，从而减少工作量。

## 五、解码 block_states.data

当一个 section 只有一种方块时，NBT 可能没有 `data`，这表示 4096 个位置都使用 palette index 0。否则 `data` 是一个 LongArray，里面保存 4096 个 palette index。

Minecraft 使用固定整数槽位将 palette index 打包进 64 位 long。正确计算方法是：

```python
bits = max(4, (palette_size - 1).bit_length())
mask = (1 << bits) - 1
values_per_long = 64 // bits
```

对于第 `index` 个方块：

```python
long_index, slot = divmod(index, values_per_long)
offset = slot * bits
value = (data[long_index] >> offset) & mask
```

不能把所有 long 拼接成连续 bit stream。比如 palette 需要 5 bits 时，一个 long 只能放 `64 // 5 = 12` 个完整值，剩余的 4 bits 不属于下一个值。错误的跨 long 解码会把普通方块误判为矿物。

NBT 中的 LongArray 元素是有符号 long。读取后要用 `& ((1 << 64) - 1)` 取得无符号位模式，再右移和掩码。

## 六、从 section index 还原 XYZ

Minecraft 的 4096 个 section index 按 X 最低、Z 居中、Y 最高的顺序排列：

```python
local_x = index & 15
local_z = (index >> 4) & 15
local_y = (index >> 8) & 15
```

世界坐标计算为：

```python
world_x = chunk_x * 16 + local_x
world_y = section_Y * 16 + local_y
world_z = chunk_z * 16 + local_z
```

因此一个扫描结果记录至少包含：

```text
X, Y, Z, 原始 block ID
```

扫描的是实际生成后的 block state，所以包含没有暴露在空气中的矿物，也不依赖矿物是否靠近洞穴、是否能被玩家直接看见。

## 七、矿物匹配和中文名称

矿物匹配使用原始 block ID，不使用中文名称。中文名称只用于 Excel 展示：

```text
minecraft:diamond_ore           -> 钻石
minecraft:deepslate_diamond_ore -> 深板岩钻石
minecraft:ancient_debris        -> 远古残骸
```

完整映射见 `references\ore-names.md`。如果用户指定新矿物，应先确认该 Minecraft 版本中实际存在这个 block ID。不要将新版本的 ID 直接套用到旧版本。

## 八、距离计算和排序

默认原点是 `(0,64,0)`。对于每个矿物坐标 `(X,Y,Z)`，计算三维欧氏距离：

```text
distance = sqrt((X-originX)^2 + (Y-originY)^2 + (Z-originZ)^2)
```

代码先计算平方距离，避免在排序阶段反复开平方：

```python
distance_squared = (x - origin_x) ** 2 \
    + (y - origin_y) ** 2 \
    + (z - origin_z) ** 2
```

排序键是：

```text
(distance_squared, Y, X, Z)
```

第一项保证越近越靠前，后面三项用于保证相同距离下结果稳定可复现。Excel 中显示的是 `sqrt(distance_squared)` 后的实际距离。

注意：这是三维直线距离。如果只想按水平 XZ 距离排序，应将公式改为：

```text
sqrt((X-originX)^2 + (Z-originZ)^2)
```

不要在用户没有要求时自行改变距离定义。

## 九、Excel 输出

通用脚本使用 `openpyxl.Workbook(write_only=True)`，避免把整个 Excel 工作簿以可编辑模式放入内存。列顺序是：

```text
X | Y | Z | Mineral | DistanceTo_(origin)
```

每个矿物方块一行，不自动把相邻矿物合并成矿脉。Excel 单个 worksheet 最多允许 1,048,576 行，其中一行是表头，所以最多写入 1,048,575 行数据。超过后创建：

```text
Minerals_1
Minerals_2
Minerals_3
```

导出完成后至少验证：

1. 输出文件可以作为 ZIP/OOXML 打开。
2. 日志中的输出行数等于扫描到的矿物方块数。
3. 第一行数据距离最小。
4. 跨 worksheet 的排序仍然连续。
5. X、Y、Z 是整数。
6. Excel 中显示的是中文名称，而不是未翻译的 block ID。

## 十、完整示例

以下示例扫描已经生成的下界 500×500 区块并导出远古残骸：

```powershell
cd "D:\Minecraft Ore Scan Src"
python -m pip install nbtlib openpyxl
python generic\scan_to_excel.py `
  --world world `
  --dimension minecraft:the_nether `
  --min-chunk -250 `
  --max-chunk 249 `
  --ore "minecraft:ancient_debris=远古残骸" `
  --origin 0,64,0 `
  --output nether_ancient_debris_sorted.xlsx
```

扫描主世界钻石：

```powershell
python generic\scan_to_excel.py `
  --world world `
  --dimension minecraft:overworld `
  --min-chunk -150 `
  --max-chunk 149 `
  --ore "minecraft:diamond_ore=钻石" `
  --ore "minecraft:deepslate_diamond_ore=深板岩钻石" `
  --origin 0,64,0 `
  --output diamonds_sorted.xlsx
```

## 十一、常见错误

### 扫不到矿物

检查世界路径和维度路径是否正确，确认目标区块已经生成并保存，确认 `--ore` 使用的是原始 block ID，而不是中文名。

### 数量明显过多

优先检查 LongArray 解码。必须使用 `values_per_long = 64 // bits`，不能使用跨 long 的连续位流算法。

### 负坐标错位

检查 region 坐标是否使用 floor division。`-1` 区块必须位于 region `-1` 的局部坐标 `31`。

### 区块数量不完整

预生成进度日志不是最终依据。重新读取每个目标 region 文件的 location table，统计目标方形中非零 entry 数量，缺失数必须为 0。

### Excel 打不开或行数少了

检查脚本是否受到 Excel 单 worksheet 行数限制，检查输出文件是否只写了一个 worksheet，检查磁盘空间，并确认脚本在 `workbook.save()` 后正常退出。

### 中文乱码

源码、文档和命令行参数使用 UTF-8。PowerShell 终端显示乱码不等于 Excel 文件内容错误；应检查 XML 的 UTF-8 内容和 Excel 实际显示。
